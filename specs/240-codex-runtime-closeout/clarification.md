## 歧义点 1：FR-004 主信号源与 transcript 交叉校验的"冲突时以谁为准"未定义

**位置**：spec.md L81，FR-004："优先读取 `.specify/runs/` 中...最新结构化事件...若存在则以其为准，transcript 仅做交叉校验（存在性/时间戳合理性），不再是唯一判据"

**歧义**：
- spec 明确了"`.specify/runs/` 存在则以其为准"，但没有定义**当交叉校验本身失败时如何处置**——即 `.specify/runs/` 记录存在、但其时间戳/sessionId 与 transcript 明显不合理（例如时间戳早于 turn 开始，或 sessionId 对不上）时：
  - 解读 A：仍然信任 `.specify/runs/` 主信号，交叉校验失败仅记日志/告警，不影响判定结果（"交叉校验"只是可观测性手段，不是否决权）
  - 解读 B：交叉校验失败应导致该记录被视为不可信，触发回退到 transcript 解析路径（"交叉校验"具有否决权，是判定链的一环）
- 两种解读对实现的影响本质不同：A 只需加一条日志；B 需要在判定器里新增一个"交叉校验失败"分支及其对应的降级/告警逻辑，且要决定该分支算不算"新盲区"（FR-004 明令禁止的"无数据可读"新盲区正是针对这类边界）。

**建议消解方向**：采用解读 A（交叉校验不具否决权，仅用于可观测性/审计），理由：
1. `.specify/runs/` 是同一次判定流程自己写入的权威记录，其存在性本身已经是强信号，赋予 transcript 否决权会重新引入"用不可靠的 Codex wire format 解析结果去推翻结构化记录"这一 FR-004 正要规避的问题；
2. spec 原文措辞"不再是唯一判据"而非"仍是可能推翻主信号的判据"，语义上更贴近解读 A；
3. 若未来发现主信号本身有伪造/篡改风险，应作为独立安全加固项，不应该悄悄塞进本 FR 的交叉校验语义里放大范围。

**是否阻塞 plan 阶段**：否——建议以脚注形式在 plan 阶段落地时明确"交叉校验失败仅记录不否决"，无需现在改 spec，但 plan.md 必须显式写出这一分支行为，避免留白到 implement 阶段才现场决定。

## 歧义点 2：FR-005 (a)/(b) 两条路径"取舍留给 plan"缺少可判定的选择依据

**位置**：spec.md L86，FR-005："两种实现方式的取舍留给 plan 阶段"

**核查结论**：这是**恰当的延后**，不构成阻塞性歧义，理由：
1. spec 已经把两条路径的**共同约束**钉死在 §5.1（"`command` MUST 为构建期已展开的绝对路径或脚本自推导路径，不依赖运行期环境变量插值"），即无论选 (a) 还是 (b)，对外行为（不依赖 Codex 未证实注入的环境变量）是一致的、可测试的；
2. (a)/(b) 的取舍属于**纯实现细节权衡**（构建期生成 vs. 运行期脚本自推导路径的可维护性/可移植性 trade-off），不影响 FR-005 的验收标准、不影响其他 FR 的接口形状，符合"延后到 plan 阶段"的合理边界；
3 反例检验：若 (a)/(b) 会导致 §5.3 `resolveCodexHome` 或 FR-006/007 的 helper 接口形状发生分叉，则应视为阻塞；但通读全文未发现这类耦合——FR-005 的路径推导与 A4 的 `CODEX_HOME` helper 是两条独立机制。

**是否阻塞 plan 阶段**：否。建议 plan 阶段给出选择结果并说明理由（例如优先 (a) 因为确定性更强、少一次运行期文件系统探测），但这属于 plan 的正常职责范围，不需要 clarify 阶段介入。

## 歧义点 3：FR-008"若确认不存在等价机制"的判定标准未定义，存在被误用为"没找到就算不存在"的风险

**位置**：spec.md L100，FR-008 plugin build 一方："若确认不存在等价机制，MUST 标记该维度为 `indeterminate`...不得回退为'猜最高版本号'"

**歧义**：
- "确认不存在"是一个需要举证的强断言，但 spec 没有说清楚**举证到什么程度才算"确认"**：
  - 解读 A（弱标准）：只要在预期路径（如 `$CODEX_HOME/` 下模仿 `~/.claude/plugins/installed_plugins.json` 的位置）没找到文件，就视为"确认不存在"，标 `indeterminate`
  - 解读 B（强标准）：必须像 `_grounding.md` §4.1 那样做过一手实测排查（含检索 `.codex-plugin/plugin.json` 的 `PluginHookSummary` 类型线索、CLI 帮助文本、app-server RPC 能力列表等多个信号源）之后仍未发现，才能下"确认不存在"的结论；否则应标 `indeterminate` 但附带"未穷尽排查"的 reason，而非直接下"不存在"的产品级结论
- 差异影响：解读 A 实现成本低，但存在"以后 Codex 出了等价机制、我方诊断代码却因为路径没写对而永远误判 indeterminate"的隐患，且这个隐患不会被任何测试捕获（因为它是"沉默的假阴性"）。解读 B 需要在诊断代码里保留一份"已排查信号源清单"作为可审计依据，实现更重但更贴近 spec 全文反复强调的"不得静默假设/不得静默判定"原则（同款措辞出现在 FR-004/FR-008/FR-009/§5.2/Edge Cases 表多处）。

**建议消解方向**：采纳解读 B 的精神但不要求过度工程化——建议 plan 阶段将"确认不存在"操作化为一个**可枚举、可复用的排查点清单**（复用 `_grounding.md` §4.1/§8 已经排查过的信号源：`.codex-plugin/plugin.json` 字段、`codex --help`/`codex doctor --json` 输出、已知路径探测），清单排查完仍无结果才落 `indeterminate` + `reason: codex-active-marker-unknown`；诊断报告的 `details` 字段应记录"已排查哪些信号源"，便于未来复审时判断该结论是否需要因上游变化而更新。此举与 FR-008 已有的"不得回退为猜最高版本号"精神一致，是同一条不确定性诚实披露原则的延伸，不新增 scope。

**是否阻塞 plan 阶段**：是——建议 plan.md 在落地 FR-008 plugin-build 检测逻辑前，先显式列出该"排查点清单"，否则容易出现"实施者随手 try 一个路径没找到就判 indeterminate"，与"确认"二字的举证强度不符，属于会导致不同实施质量的真实歧义。

## 歧义点 4：FR-009"探测手段留给 plan/实施阶段选择"叠加"若所有候选手段都不可行"的兜底缺失

**位置**：spec.md L107，FR-009："该 check 的探测手段留给 plan/实施阶段选择（如经 app-server RPC `hooks/list`...），但 spec 层面钉死：探测失败/不可判定时该维度标记 `indeterminate`"

**核查结论**：这一处**已经有兜底**，不构成阻塞性歧义——"探测失败/不可判定时标记 `indeterminate`"本身就是覆盖了"所有候选手段都不可行"这一最坏情形的兜底行为，跟 FR-008 的 plugin-build/MCP-server 维度采用完全同构的降级策略（indeterminate，不静默判定为已信任/一致）。§9 未决问题第 4 条也已如实标注"信任记录的持久化位置未确证，需在 plan/implement 阶段先实测确认"，说明 spec 作者已经意识到这条路径存在不确定性并做了显式挂账，而非遗漏。

**唯一需要注意但不算歧义的点**：spec 没有规定"探测尝试次数"或"探测手段是否要多路径 fallback 后才判 indeterminate，还是单一路径失败即判"。但这属于与歧义点 3 同类的实现细节，其影响面（是否要维护一份多路径 fallback 逻辑）不改变对外契约（indeterminate 语义不变），建议留给 plan 阶段决定即可，不需要 clarify 阶段升级为阻塞项。

**是否阻塞 plan 阶段**：否。

## 歧义点 5：§5.2 `overallStatus` 计算规则文字表述有轻微冗余但语义完整，非阻塞

**位置**：spec.md L163，§5.2："`overallStatus` 的计算规则：任一 `check.status === 'indeterminate' || 'fail'` 时不得为 `ok`"

**核查结论**：该规则覆盖了"indeterminate/fail → 非 ok"这一方向，配合 L148 `overallStatus` 枚举 `ok | warning | fail`，可以推出的完整真值表是：
- 无 fail 且无 indeterminate 且无 warning → `ok`
- 无 fail、无 indeterminate，但有 warning → `warning`（隐含，未显式写但符合枚举语义与 Edge Cases 表整体精神）
- 有 indeterminate（无论有无 fail）→ 非 `ok`，但落到 `warning` 还是 `fail` 未显式规定
- 有 fail → 非 `ok`

**这里确实存在一个小歧义**：indeterminate 单独出现时，`overallStatus` 该落 `warning` 还是 `fail`？spec 只说"不得为 ok"，两个值都满足这一条件，两个称职实施者可能选不同的值：
- 解读 A：`indeterminate` 视同 `warning` 严重度（因为它不是明确的"错误"，只是"读不到"，与 fail 语义不同）
- 解读 B：`indeterminate` 视同 `fail` 严重度（因为诊断的核心目的是"杜绝旧 MCP server 静默服务新 worktree 的已知风险"，读不到本身就是高风险信号，应该用最高严重度提醒用户）

这个歧义会影响 `repo:check`/CI 场景下人是否会第一时间注意到（若走 `warning` 通道，某些下游消费方可能选择性忽略；若走 `fail`，会更显眼但也可能造成"诊断工具本身不阻断，为何 overallStatus 却报 fail"的认知落差，因为 FR-008 明确"诊断不阻断，定位与 judge-snapshot-doctor.mjs 一致"）。

**建议消解方向**：`indeterminate` → `warning`（而非 `fail`），理由：
1. `fail` 语义上应该保留给"明确判定为不一致/漂移"这一确定性结论，`indeterminate` 本质是"我们不知道"，混入 `fail` 会让下游消费者（未来若真的接入 CI 软阻断）无法区分"确定有问题"与"暂不确定"，削弱 `indeterminate` 态存在的意义（§5.2 本身也说明新增 `indeterminate` 就是为了把"读不到"和"确实不一致"的语义分开）；
2. 与"诊断不阻断"的产品定位一致——`warning` 比 `fail` 更贴近"提醒但不视为硬性错误"的调性。

**是否阻塞 plan 阶段**：是（轻微）——建议在 plan.md 里把这条真值表显式补全（尤其是 indeterminate 单独出现时的映射值），因为这是一个会被单元测试直接断言的具体行为，若两个实施者各自选择不同映射，测试断言会不一致，且没有 spec 依据可以裁决对错。

## 歧义点 6：FR-003 failure-degrade "与 Claude 侧同类脚本的 fail-open 语义做对比记录"——"记录"产出物与验收方式未定义

**位置**：spec.md L75，FR-003 failure-degrade 路径："并与 Claude 侧同类脚本的 fail-open 语义做对比记录"

**歧义**：
- "记录"二字没有说明产出形态，至少存在三种合理解读，且互相之间验收标准完全不同：
  - 解读 A：产出物是**代码注释/commit message**里的一段文字说明（轻量级，人工可读，无自动化验收）
  - 解读 B：产出物是 spec/plan/或独立 markdown 文档里的**对比表格**（Codex fail-open 行为 vs. Claude fail-open 行为逐项对照），作为设计文档的一部分，同样无自动化验收但要求更结构化
  - 解读 C：产出物是**测试用例本身**——即 FR-003 的 E2E 测试套件里包含一条断言，显式验证"Codex 侧异常退出的降级行为"与"Claude 侧同类脚本异常退出的降级行为"在某个可观测维度上（如 exit code 处理、是否阻塞 turn/session）一致或不一致，测试失败即代表行为漂移
- 三种解读对实施工作量和验收严谨度差异巨大：C 需要新增跨运行时的对比测试基础设施（可能相当分量），A/B 只是文档产出。Edge Cases 表 L185 重复了同样的措辞"行为需与 Claude 侧同类脚本的 fail-open 语义对比记录，差异需显式标注"，"显式标注"进一步暗示这更像是文档/报告产出（解读 A/B），而非可执行断言（解读 C），但 spec 全文没有明说，也没有把这条纳入 §7 回归护栏或任何"MUST 有自动化测试覆盖"的清单。

**建议消解方向**：采纳解读 B（结构化文档对比，非新增自动化测试）：
1. FR-003 本身的验收重心是"failure-degrade 路径不导致 turn 挂起/产品崩溃"（这一点已有明确、可自动化验收的断言目标），"对比记录"是这条主断言之外的**说明性附加要求**，用于给未来维护者提供决策依据（例如为何不需要让两个运行时行为完全一致），不是新的独立验收项；
2. 若要求解读 C，会让 FR-003 的验收面无限扩大（需要精确定义"一致"的判据维度、需要维护双运行时对比 fixture），而 spec 全文其余部分（包括 §7 回归护栏）都没有提及这类跨运行时行为一致性测试的基础设施，突然在这一处引入不符合 spec 的整体颗粒度；
3 建议 plan 阶段将该对比记录的落点明确为 plan.md 或 tasks.md 的设计说明章节（或直接写入相关脚本头部注释），不设为独立可测试的验收标准。

**是否阻塞 plan 阶段**：是（轻微）——不是因为该问题复杂，而是因为它决定 FR-003 的任务分解里是否要拆出一个独立 task（写对比文档 vs. 写对比测试），plan 阶段的 tasks 颗粒度会因这个选择而不同，建议 plan.md 显式点明产出形态是"文档"而非"测试断言"，避免 tasks 阶段两种理解都有task 产出。

## 总结

| # | 歧义点 | 阻塞 plan？ | 建议消解方向摘要 |
|---|---|---|---|
| 1 | FR-004 交叉校验失败时是否有否决权 | 否 | 不具否决权，仅可观测性用途 |
| 2 | FR-005 (a)/(b) 取舍延后是否恰当 | 否（本身无歧义，延后合理） | 维持延后，无需现在决策 |
| 3 | FR-008"确认不存在"的举证标准 | 是 | 要求 plan 列出可枚举的排查点清单，非"没找到就算" |
| 4 | FR-009 所有候选手段不可行时的兜底 | 否（已有兜底） | 沿用既有 indeterminate 兜底 |
| 5 | §5.2 indeterminate 单独出现时 overallStatus 落哪个值 | 是（轻微） | 建议 `indeterminate → warning`，需 plan 显式写入真值表 |
| 6 | FR-003 failure-degrade"对比记录"的产出形态 | 是（轻微） | 建议为文档产出而非新增自动化断言，plan 需点明 |

共 3 处（#3/#5/#6）建议在 plan 阶段前显式消解并写入 plan.md，避免"两个称职实施者读同一句话做出不同实现"；其余 3 处（#1/#2/#4）经核查为已有合理默认或恰当延后，不构成阻塞。整体上 spec.md 质量较高，绝大多数条款已通过"MUST NOT 静默判定"类措辞和 `_grounding.md` 强绑定收窄了解读空间，未发现涉及安全/合规/核心范围的 CRITICAL 级歧义。
