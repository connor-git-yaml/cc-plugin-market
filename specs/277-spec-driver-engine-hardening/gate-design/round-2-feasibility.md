### 1.1 测量方法（可复现）

```bash
# 逐 feature 取「主题行含 (F<NNN>」的全部 master commit，按 commit 粒度累加 numstat，
# 避免用 first^..last 区间（master 上多 feature 交错会把别人的改动算进来）
for f in F262 F263 F264 F266 F267 F268 F269 F270 F271 F272 F273 F274 F275; do
  git log --format='%H' --grep="($f" master > /tmp/cs.txt
  while read c; do git show --numstat --format= "$c"; done < /tmp/cs.txt > /tmp/ns.txt
  awk '$1!="-"{a+=$1;d+=$2} END{print a,d}' /tmp/ns.txt            # 总行数
  awk '{print $3}' /tmp/ns.txt | sort -u | grep -c .               # 总文件数
  # code-only：剔除 specs/ docs/ 与一切 *.md
  awk '$3 !~ /^specs\// && $3 !~ /^docs\// && $3 !~ /\.md$/ ...' /tmp/ns.txt
done
```

注：zsh 下 `for c in $cs` 不做词分割，必须走 `while read`；`tac` 在 macOS 上是 `tail -r`。

### 2.4 本节最重要的结构发现：4 条 FR 会随 Tier 1 被裁剪而**自动变真**

FR-035（脚本不得与 prompt 有语义落差）、FR-037（只允许 `import node:`）、FR-038（脚本不得内嵌编排事实源）、FR-045（脚本 catch 分支禁 fail-open）**四条的主语都是「本 Feature 新增的脚本」**。若 plan 把 Tier 1 全部裁剪（不写任何脚本），这四条的前件为空，全部**空真（vacuously true）**地达成。

### R2-F01 `FR-060` 的「显式接受」在唯一一次 GATE 暂停里退化为一次性批准长清单

**对照 R1**：R1-C18 的后半段（「已裁剪是无准入门槛的合法终态」）。R1 提出「须有准入门槛」，spec 用 FR-060 加了门槛；**本条攻的是这道门槛的强度，R1 未涉及**。

**实测链条**：

1. `plugins/spec-driver/skills/spec-driver-feature/SKILL.md:705-711` 实测：`is_hard_gate=true` 时 `GATE_DECISION="PAUSE"`，用 `AskUserQuestion` 向用户展示**制品摘要**。`config/orchestration.yaml` 中 `GATE_DESIGN` 的 `hard_gate_modes: [feature]` ⇒ 接受者确实是**用户**而非 LLM 自身。这一点 spec 站得住，不是「自我接受」。
2. 但 `gate-design/round-2-delta-verify.md:21` 记录 R1-C13 的处置是：FR-021 明写「**收敛循环必须在单次 `GATE_DESIGN` 暂停之前闭环**」。也就是说全流程只有**一次**暂停。
3. FR-049 明写「**不得新增任何用户确认点**，不得加重 GATE 的交互负担」⇒ 不能给裁剪项加逐条确认。
4. FR-060 的要求字面是「**单列成组**并被显式接受」——「成组」本身就是批量语义；spec 未对该组设**任何上界**，未要求逐条接受，也未要求 GATE 展示的是 FR 全文而非「制品摘要」。

**后果**：唯一一次用户暂停里，出现一份「本卡裁剪的 MUST 项清单（N 条）」，用户只能整组批准或整组拒绝。整组拒绝会退回 plan 重做，代价远高于批准；这构成与 R1-C04 同型的**严格占优路径**（R1-C04 攻的是「不写矩阵优于写矩阵」，本条是「整组批准优于整组拒绝」）。

**spec 防了吗——部分防了，防漏三处**：
- 防到的：接受者是用户（不是自我接受）；留痕字段要求 FR 编号 + 强度标注 + 理由 + gate 时点。
- 没防到的：(i) 组规模无上界；(ii) 无「超过 K 条须逐条」的分档；(iii) GATE 展示的是「制品摘要」，摘要的失真面未登记——而 spec 自己在 FR-030 里刚刚要求「引用历史内容必须附原文片段，禁止只写结论转述」，同一份 spec 对**给用户看的裁剪清单**没有提出同等的原文化要求。
- **诚实性口径缺席**：spec 对 FR-006 明确写了「所谓『拒绝』实为自我拒绝，是留痕而非机制」这条诚实降级（见「不测量什么」节）。FR-060 是同一族的判定条款，却**没有任何一条对应的强度声明**。全文检索「显式接受」只命中 FR-060 / SC-001 / Key Entities 三处，无一处讨论接受的粒度或摘要的信息损失。

**与 §1 基线的联动**：本卡 67 FR 是近 6 个 spec 的最高值、比中位数（25）多 168%。plan 必然大幅裁剪不是假设，是**从基线外推的必然**。所以这份长清单不是边界情况，是主路径。

### R2-F02 `SC-013` 的下界 `M_min ≥ 1` 使「8 项做成 1 项」全绿，且下界值由被约束方自定

**对照 R1**：R1-C18 前半段（「SC-001 把裁剪计入分子 → 8 项全裁剪仍 100%」）。R1 要求「设下界」，spec 用 FR-061 + SC-013 设了；**本条攻的是这个下界的取值与其确定方式，R1 未涉及**。

**实测**：SC-013 原文——「换算式：实际实现项数 ÷ 需求项总数 = M ÷ 8 ≥ M_min ÷ 8……**本 spec 给出的硬下界为 M_min ≥ 1**（FR-061 只禁 0），具体 M_min 由 **plan 阶段确定**并留痕，且不得低于 1」。

**下界有意义吗——没有，理由三条**：

1. **数值上等于「非零即可」**。换算式：最松合规交付 = 1 ÷ 8 = **12.5%**（单位：需求项）。它把「零交付」挡在门外，但对「12.5% 交付」与「100% 交付」不作区分。而本卡真正要防的病根是 F270 的「范围在 plan 阶段静默收缩」——F270 事后口径是 6 真达成 ÷ 13 = 46.2%，**远高于 12.5%**。也就是说：**这条下界连 F270 那次失败都拦不住**。
2. **真下界由被约束方设定**。「具体 M_min 由 plan 阶段确定」——而 plan 正是 §1.4 实证的稀释发生地。这与 spec 自己在 FR-032 里点名的反模式同型：「『已核实』不是自助豁免桶……等于让**被测方自行选定分母**」。同一份 spec 隔 60 行就把这个结构重犯了一次，只是这次自选的是分子的下界而不是分母。
3. **与 §2.4 叠加后可得「零代码全绿」**。把 Tier 1（11 条，含全部 4 个校验器）整组裁剪、只交付 1 个需求项：SC-001 = 100%（裁剪经 FR-060 接受即入分子）、SC-013 = 1 ÷ 8 ✓、FR-035/037/038/045 因无脚本而**空真**达成、SC-011（五条命令零失败）因改动面缩小反而**更容易**达成。换算式：此路径下的代码交付量 = 0 ÷ 11 = **0%**（单位：Tier 1 FR 条），而 Success Criteria 面上无一条转红。

**真正的 blocker 是并行满载**：

- FR-051 **要求** F276 与本卡并行进行（同一台开发机、共享 `node_modules`）。满载不是异常场景，是**设计安排**。
- `specs/272-.../verification/verification-report.md:35` 实测满载下：耗时 **828s**（对照干净 64.62s，**13× 拖慢**），`7 failed` / `9 failed` 两次，伴随 5-6 个 `Timeout calling "onTaskUpdate"` birpc 假红签名；`:30` 另记录一次 `Duration 407.91s`。
- 本仓已登记 4 类预存负载敏感 flaky（`watch-command` / `batch-orchestrator-incremental` / `community-analysis` / `cli-e2e --version`），F272 又新增 2 条未入清单。

**冲突点**：SC-011 要求「零失败命令数 ÷ 命令总数 = 5 ÷ 5 = 100%」，是一条**布尔零容忍**判据。在满载下它几乎必然先判红，然后需要走本仓已有的「满载 flake 判定协议」（隔离重跑绿 + 与改动面零交集 + 干净环境复跑）——即**每次修订至少 2 次全量**。

换算式（保守，按对抗收敛 3 轮估，依据：F266 三轮 / F264 判据被推翻两次重写 / F270 三轮五路）：
- 干净串行：3 轮 × 2 次全量 × 90s = **540s ≈ 9 min**
- 并行满载：3 轮 × 2 次全量 × 828s = **4968s ≈ 83 min**（单位：秒 / 分钟）

**spec 的缺席**：全文检索 `flaky` / `假红` / `满载` / `负载敏感` **命中数 = 0**（单位：命中行）。SC-011 没有定义「什么样的失败可以判为假红而不计入失败数」。这给执行者留了三条路，每条都坏：(a) 放弃与 F276 并行 → 直接违反编排安排；(b) 每次都做归因 → 成本 ×2 且无 spec 依据；(c) **把假红判成绿** → 这正是本卡要收口的 fail-open 形态，且发生在本卡自己的护栏上。

## 4 可实施性判定

### 4.1 判定：**必须分批**

不是「可一次交付」——67 FR / 15 组件 / 14 接口 / 触及 6 条链路（5 既有 + 1 新建），横向面宽于本仓唯一同量级先例 F270，而 F270 的结局是「范围在 plan 阶段静默收缩」（§1.4）。

也不是「必须削减范围」——本卡的每一条 FR 都可追溯到 R1 的实测缺陷，删掉任何一条都是把已知洞留着。削减会让整轮对抗收益归零，正是本次审查要防的事。

**分批 ≠ 裁剪**。二者的差别是判定终态：
- 「裁剪」在本 spec 里是**合法终态**，经 FR-060 一次接受后即计入 SC-001 分子（100% 达成），无人再追。
- 「移交后续卡」是**未完成态**，须有编号与落点，下一轮 milestone review 会看见。

### 4.2 分批必须写进 spec，不能留给 plan

这是本节最重要的一条建议，依据是 §1.4 + R2-F01 + R2-F02 三处独立证据指向同一件事：**plan 阶段是本仓已实证的稀释发生地，而本卡把「分批多少」「下界多少」两个关键量都交给了 plan 自己定**。

具体两处必须在 spec 阶段钉死：

1. **`SC-013` 的 `M_min` 必须由本 spec 给出具体数值，不得写「由 plan 阶段确定」**（当前值 `M_min ≥ 1` 等于「非零即可」，连 F270 那次 46.2% 的失败都拦不住，见 R2-F02）。建议按 §4.3 的核心集直接钉为「8 项需求项中第 1 / 3 / 5 / 6 / 7 项（对应核心集）必须实现，`M_min = 5`」，换算式：5 ÷ 8 = 62.5%（单位：需求项）。
2. **`FR-060` 须补一条组规模分档**：被裁剪的 MUST 项超过 K 条时不得整组接受（K 由本 spec 给值），且 GATE 展示须给出被裁剪项的**原文**而非摘要（与 FR-030 对历史引用的原文化同标准）。
