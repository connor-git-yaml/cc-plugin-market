## B-1

### 先说守住的部分（原攻击卡在哪）

R1-C04（兼容分支是严格占优路径）的原构造现在卡在 `spec.md:334` FR-042 的这一句：

### 构造 P1（判据字面命中）：FR-060 点名的那道 GATE 在结构上永远收不到裁剪登记

`spec.md:366` FR-060 逐字：

> 标注为 `[必须]` 或 MUST 的项若要裁剪，必须在 `GATE_DESIGN` 的输出中**单列成组**并被**显式接受**……也不得以「plan 里已写理由」替代显式接受……显式接受的留痕须包含：被裁剪的 FR 编号与其强度标注、裁剪理由、接受该裁剪的 gate 时点。

而被接受的对象产于何处，`spec.md:262` FR-004 逐字：

> 任何在矩阵中标为「未认领」的 FR，必须在 **plan** 的「裁剪登记」具名章节中出现并写明裁剪理由

**实测编排事实（`plugins/spec-driver/config/orchestration.yaml`，`feature` mode 的 phase 序列）**：

```
      # Phase 3.5: GATE_DESIGN（编排器执行）
      - id: "3.5"
        name: gate_design
        gates_after:
          - GATE_DESIGN
      # Phase 4: 技术规划
      - id: "4"
        name: plan
        gates_before:
          - GATE_DESIGN
        skip_if_exists: "plan.md"
```

`GATE_DESIGN` 是 Phase **3.5**，`plan` 是 Phase **4**。两处 `gates_after` / `gates_before` 指的是**同一次**门触发，位置在 spec-review 之后、plan 之前。门触发时 `plan.md` 尚不存在。

暂停时展示什么，`plugins/spec-driver/skills/spec-driver-feature/SKILL.md:723-726` 逐字：

> \# PAUSE 执行方式：
> \# - 列出当前 Gate **之前**生成的制品清单和摘要
> \# - 使用 AskUserQuestion 提问："GATE_{name} 审查：是否继续？"

即 `GATE_DESIGN` 暂停展示的是 Phase 0~3 的制品（`spec.md` / research / spec-review 报告），**结构上不可能包含 Phase 4 才产出的 plan 裁剪登记**。

**因此 FR-060 要求的「显式接受」在 `feature` mode 下不可达**，攻击者无须构造任何东西——它是唯一可能的终态：

1. plan（Phase 4）产出矩阵，需裁剪 `FR-052`（MUST · [必须]）。
2. FR-060 要求该裁剪经 `GATE_DESIGN` 显式接受。该门已于 Phase 3.5 关闭。
3. spec 自己的护栏堵死了补一道门：`:346` FR-049 逐字「**不得新增任何用户确认点，不得加重 GATE 的交互负担**」。`:292` FR-021 同向（收敛循环须在**单次** `GATE_DESIGN` 暂停之前闭环）。
4. plan 只能在裁剪登记里自填 FR-060 要求的三个字段，其中「**接受该裁剪的 gate 时点**」只能是一个自述值——真实的 `GATE_DESIGN` 输出制品里不会有这一条。
5. verify 计 `:434` SC-001 分子时判「**经 FR-060 显式接受的**已登记裁剪项」，判据只能是读裁剪登记里那个由 plan 自填的字段；**没有任何第三方证据源可供交叉核对**（FR-053 的 `repo:check` 守护项断言的是 effective 配置里 `GATE_DESIGN` 是硬门禁，**不读该门的输出内容**）。

终态：`FR-052` 从「未认领」转入「已裁剪」、计入 SC-001 分子、交付判定不再追它，而**事实上不曾经过任何 GATE 的显式接受**——判据「让『未认领 FR』在不经 GATE 显式接受的情况下从最终交付判定中消失」逐字命中。

更尖的一点：FR-060 明文禁止的替代形态「**不得以「plan 里已写理由」替代显式接受**」，在当前编排时序下**恰恰是唯一物理可能的形态**。该条款禁止的是它自己唯一能落到的地方。

**该时序在需求项 1 标为「强制」的全部三个 mode 下一致成立**（实跑 `orchestration.yaml` 三段 mode 定义）：`feature` — GATE_DESIGN 为 Phase 3.5 的 `gates_after`、Phase 4 `plan` 的 `gates_before`；`story` — GATE_DESIGN 为 Phase 2 `specify` 的 `gates_after`、Phase 3 `plan` 的 `gates_before`；`implement` — GATE_DESIGN 为 Phase 2 `plan` 的 `gates_before`（该 mode 下 plan 是首个产出 phase，门在其之前）。**三个 mode 全部是「门在前、plan 在后」，无一例外**，故 P1 不是某个 mode 的特例。三个 mode 下 plan 之后的门只有 `GATE_ANALYSIS` / `GATE_TASKS`，而 FR-060 逐字点名的是 `GATE_DESIGN`。

**与上轮对照**：R1-C18 前半 / R2-F01。R2-F01 攻的是「显式接受退化为一次性批准长清单」，处置是 K=3 分档 + 逐条多选 + 展示原文（`:366` 三项接受强度约束）。**三项约束全部建立在「`GATE_DESIGN` 暂停时看得见裁剪清单」这一未登记前提上**，而该前提被编排器 phase 序列证伪。R2 三路（D/E/F）均未查 phase 序列，**计新增**。

### 构造 P2（反稀释度量结构性失明）：8 需求项的分区只覆盖 67 条 FR 中的一半

`:375` FR-061 的立条目的逐字：

> 必须对实现量设下界，使「8 项需求全部裁剪」在 Success Criteria 面上**可见为不达成**

其落地条目 `:468` SC-013 的分子分母单位是**需求项**（`M ÷ 8`，M_min = 7）；`:434` SC-001 同样是需求项（`8 ÷ 8`）。而需求项 → FR 的分区，取自 `:398-406` mode 分层矩阵第 1~8 行的括注（`FR-001~007` / `FR-008~013` / `FR-020~025` / `FR-026~029` / `FR-014~019` / `FR-030` / `FR-031` / `FR-032~033`），外加 `:468` SC-013 把 `FR-064` 归入需求项 2（`:799` 已登记该处与矩阵字面区间的口径外溢，并裁定以 SC-013 为准）。

**实算**（脚本核算，取 SC-013 口径）：

- 需求项分区覆盖的 FR = **34 条**（`FR-001~033` 33 条 + `FR-064` 1 条），单位：FR 条
- 全部 FR = 67 ⇒ **无任何需求项归属的 = 33 条**；换算式 67 − 34 = 33，占比 33 ÷ 67 = **49.3%**
- 核心集（边界 A）= 63 条 ⇒ **核心集内无需求项归属的 = 33 条**；换算式 63 − (34 − 4) = 33，占比 33 ÷ 63 = **52.4%**（减 4 为移交的 `FR-010~013`）
- 该 33 条为：**`FR-034 ~ FR-063` + `FR-065` + `FR-066` + `FR-067`**

**这 33 条正是本卡的承重条款集中区**——`FR-042~045`（向后兼容与降级）、`FR-052/053`（门不可绕过 = 承重项 B-4 的全部内容）、`FR-054~058`（既有冲突收编 = B-3 的全部内容）、`FR-059/060/061`（交付判定合并律与裁剪准入 = 反稀释机制自身）、`FR-062/063`（执行证据与缺席后果）、`FR-046~051`（YAGNI 标注与回归护栏）、`FR-035~041`（落点与同步纪律）。

后果：把这 33 条**全部**裁剪掉，SC-001 仍为 `8 ÷ 8 = 100%`（八个需求项各自的归属不受影响），SC-013 仍为 `M = 7 ≥ M_min = 7`（七个完整需求项的 FR 全在另外 34 条里）。**FR-061 明确要防的「合规的零交付」形态，在 FR 层面换个位置就完全避开了它的度量**——它防住的是「8 项需求全部裁剪」这一种写法，防不住「把 52.4% 的核心集 FR 裁掉但八项需求各留一条命」。

诚实边界（不夸大）：这 33 条并未从**交付判定**里完全消失——`:264` FR-006（未认领未裁剪 ⇒ 未实现）与 `:365` FR-059（合并律）在 FR 层面仍会把它们拉红。**失守的是 FR-061 / SC-013 / SC-001 这一层**，即 R1-C18 后半、R2-F02 的收口落点：反稀释的**可见性**度量对本卡一半的 FR 结构性失明，而 spec `:468` 却把 M_min = 7 表述为「排除的是『合规的零交付』与『大幅稀释』两种形态」。合读 P1（FR-060 那道闸不可达）与 P2（FR-061 的尺子只量一半），R1-C18 的两条处置在 R3 下**都不成立**。

**与上轮对照**：R1-C18 后半 / R2-F02 的延伸。R2-F02 攻的是「M_min ≥ 1 = 非零即可 + 由 plan 自定」，处置是钉死 7。**处置只动了阈值，没有核对该阈值所在分区的覆盖面**，R2 三路均未做 FR→需求项的满射核算，**计新增**。

### 构造 P3（较弱，附带登记）：假认领在 FR-003 交叉校验下仍是零成本

`:261` FR-003 的机械判据逐字：

> 矩阵「认领 Phase」列的每一个取值必须 ∈ 该 `plan.md` 实际定义的 Phase 集合；取值不在集合内的行一律判为**失去认领**

`:264` FR-006 亦逐字承认认领可伪造，并给出解法：

> **「某 Phase 认领了某条 FR」本身也是 plan 自述、与被约束的产出同源且可伪造**……因此该认领只有在其 Phase 名 ∈ plan 实际定义的 Phase 集合时才被接受

**该解法只堵住「Phase 名不存在」这一种伪造形态**，堵不住「Phase 名存在、但该 Phase 的任务内容与该 FR 无关」。plan 作者本来就要定义 Phase，在认领列多写几个 FR 编号是零成本；`:359` FR-056 要求的「每条未被裁剪登记的 FR 至少有一个对应任务」，写一条 `T0XX` 同样零成本。此后该 FR 从未进入「未认领」分支，FR-004 / FR-006 / FR-060 全线不触发，只剩 verify 逐条判「已实现（附证据）」这一步——而那一步是 `:264` FR-006 自己承认没有第三方裁决位的自述。

判弱的理由与诚实登记：`:379` FR-062 要求矩阵对账结论附命令原文与原始输出，但其覆盖对象是**矩阵对账**（三值比对、Phase 集合校验这类机械检查），逐条「已实现」判定是语义判断、不存在「产生该结论的命令」，FR-062 在这一步空载。因此 P3 的成立依赖 verify 在语义判定上失真，属 spec 已在 `:480` 免责节登记的能力边界（「执行者仍可能在证据本身上失真，这不在矩阵的判定能力内」），**不单独计 CRITICAL**，仅登记：本卡把「未认领」变可见，但**没有让「假认领」变可见**，而后者的成本与前者相同（各写一行）。

**与上轮对照**：R1-C07 / W-C7 的残余面，spec 已部分登记，**不计新增**。

## B-2

**守护判据**（逐字）：verify 是否仍能在同一次推理内把矩阵与锚一起改到自洽。

**判定：失守**（2 条独立构造，其中 B-2-α 为主）。

### 与上轮对照

对应 R1-C03 + R2 delta 面 A-1。R2 A-1 的原攻击是「冻结哈希与被冻结物在同一写面（tasks 制品）内，verify 持 `Bash` 可连矩阵带哈希一并 `sed -i`，比对照样一致」。R2 段 2 的收口是把冻结值改为**编排器持有 + 注入 verify prompt**，理由逐字（`spec.md:263` FR-005）：

> 此设计的要害是介质而非算法：verify 实测持有 `Bash`（见 FR-016），它能改磁盘上的 `plan.md` 与 tasks 制品，但**改不了编排器发给它的 prompt 文本**，因此注入值是本卡唯一一个在 verify 写面之外的比对源

**该句本身成立**——verify 确实改不了自己收到的 prompt。**但它论证的是「注入值的原件不可篡改」，不是「verify 报告出来的 ① 不可篡改」。** 这两个量之间需要一个比对环节，而 spec 全文没有这个环节：FR-005 只要求 verify 自己「并列报告三个值……并给出两两比对结论」，**没有任何条款要求编排器（或任何第三方）拿它手里持有的那份注入值去核对 verify 报告的 ①**。原件在会话外部，但**读数在会话内部**，判定消费的是读数。

### 构造 B-2-α（谎报 ①：原件在外、读数在内，无人比对）

可复现步骤（全部在 verify 的同一次推理内，全部使用 verify 实测持有的 `Bash`）：

1. verify 收到 prompt，注入块含冻结值 `H0`。
2. `sed -i` 改 `plan.md` 覆盖矩阵——把 `FR-052` 的认领列由「未认领」改为某个**确实存在于该 `plan.md` Phase 定义章节**的 Phase 名（满足 `spec.md:261` FR-003 的「取值 ∈ Phase 集合」交叉校验）。
3. 现算 ③ = `H1`。
4. `sed -i` 改 tasks 制品里的冻结值 → ② = `H1`。
5. 在 `verification-report` 中写：①`H1` / ②`H1` / ③`H1`，「两两比对一致 ⇒ 该项 PASS」。

第 5 步是唯一的新增动作，且它**不是「改锚」而是「谎报锚」**——但 FR-005 的判定输入只有 verify 写出来的那三个字符串，二者在判定面上等效。FR-005 的两条罚则都不触发：「三值中任一不一致」不成立（报告里一致），「注入值缺席」不成立（报告里有值）。

**卡点在哪儿本应存在、而现在不存在**：spec 在 `:264` FR-006 已经把这条锚认定为撤销「人工结论被拒绝」之后的唯一替代承重点——

> 真正把冲突锚定住的是两条机械校验：**FR-005 的编排器注入冻结值三值比对**（锚点是编排器写给 verify 的 prompt 文本——verify 能改磁盘但改不了自己收到的 prompt）

而同一段落在 20 行之上刚刚论证过：prompt-only 路径上「写下『已实现』与判定『该结论应被拒绝』是同一次 LLM 推理的产物……所谓『拒绝』实为自我拒绝，是留痕而非机制」。**「verify 报告 ① = H1」与「verify 判定三值一致」同样是同一次推理的产物**，FR-006 撤销 over-claim 时用的那把尺子，量到 FR-005 自己头上时没有再量一次。

与 A-1 的差别只有一点、且只在**事后审计**层面成立：编排器手里留着 `H0` 原件，事后任何人拿 `H0` 与报告里的 ① 一比即露馅；而 A-1 的构造在磁盘上不留原件。**这是「可追溯性」的提升，不是「判定链闭合」的提升**——交付判定在 verify 产出报告的那一刻就已经走完，没有任何条款把这次事后比对写进判定链。

### 构造 B-2-β（`resume` 兜底把注入值来源换回 verify 写面，无需谎报）

`spec.md:263` FR-005 的 resume 分支原文：

> **经 `resume` 恢复而编排器上下文已失时**：注入值来源改为 `.specify/runs/` 运行记录中留存的冻结值（本地运行态，F239），或 `GATE_TASKS` 之后的 commit 对象中的 tasks 制品版本（若已 commit）；**两者皆无 ⇒ 注入值缺席 ⇒ 按上句判「未执行（缺席）」**

两条兜底是「或」关系，第二条（commit 对象）是真外部锚，第一条不是。实测：

```
$ git check-ignore -v .specify/runs/
.gitignore:55:.specify/runs/	.specify/runs/
$ git ls-files .specify/runs
(空 ⇒ 未被 git 追踪)
```

`.specify/runs/` 是 gitignore 内的**未追踪本地磁盘目录**（CLAUDE.md 仓库级同步约定亦逐字写明它「属于本地运行态，保持忽略，不要当作长期人工事实源」）。verify 持 `Bash` ⇒ 该目录在 verify 写面之内。**这一支把 FR-005 自己刚论证过的「介质而非算法」要害整个撤销了**：注入值来源从「verify 改不动的 prompt 文本」换成「verify 改得动的磁盘文件」，而条款把两者并列为等价来源。

更要害的是**谁判定该分支被触发**。FR-005 写的触发条件是「经 `resume` 恢复而编排器上下文已失时」，**未指定判定者，也未给判据**。verify 是该时点唯一在场的执行者，因此它可以声称「本次经 resume 恢复、注入块为空」，从而**合法地**把 ① 的来源切到 `.specify/runs/`，写入 `H1`，三值一致——**全程不需要谎报任何东西**。

这是 **R1-C04 的同型复发，且复发在本卡最承重的那条锚上**。同一份 spec 在 `:334` FR-042 已经为完全同型的问题立过标准并逐字写明其严重性：

> **但兼容分支的触发判据不得是「矩阵章节在不在」**：章节在不在是**被检者完全可控的量**……触发条件必须绑定**独立于制品内容、被检者改不动的外部事实**……**判据本身因故取不到时……按不成立处理走 fail-loud**

### 后半「M_min 是否与边界一致且不由 plan 自定」——**失守**

**「不由 plan 自定」这一半守住。** `:468` SC-013 逐字「**M_min 由本 spec 钉死为 7，不由 plan 自定**（R2-F02 的收口落点）」「**plan 只可在 ≥ M_min 上加严，不得放宽**」，并预置了替代边界下的重钉条款。R2-F02 的原攻击（`M_min ≥ 1` = 非零即可 + 由被约束方自定分母）**卡在这两句上，不再成立**。

**「与边界一致」这一半失守。** 数值上 7 对得上（`:709`「完整实现项 7 ÷ 需求项总数 8 = 87.5%」，与 SC-013 逐字一致），但**两者的计数分区对不上**，而 spec `:709` 把这称作「该换算式与 SC-013 钉死的 `M_min = 7` **逐字一致**」——一致的只是数字 7，不是它所约束的集合。

**问题一：M_min = 7 在边界 A 下是等式而非下界，使 FR-060 成为死通道。**

边界 A 下需求项 2 结构性不可能完整（`FR-010~013` 移交），故 `:468` SC-013 口径下 **M 的理论上界 = 7 = M_min**。下界与上界重合 ⇒ 约束退化为等式 ⇒ 七个完整需求项覆盖的 FR **零裁剪余量**。

实算：七个完整需求项（1/3/4/5/6/7/8）覆盖 `FR-001~007` + `FR-014~019` + `FR-020~025` + `FR-026~029` + `FR-030` + `FR-031` + `FR-032~033` = **27 条**（换算式 7+6+6+4+1+1+2 = 27，单位：FR 条）。裁剪其中任意一条 ⇒ 该需求项变「部分」⇒ M ≤ 6 < 7 ⇒ SC-013 不达成 ⇒ `:365` FR-059 合并律判交付不通过。

**后果：`:366` FR-060 精心设计的三项接受强度约束（K=3 分档整组接受 / 同一次暂停内多选逐条接受 / 展示 FR 原文）在这 27 条上没有任何成功路径**——用户在 GATE 上依 FR-060 显式接受 1 条 MUST 裁剪之后，SC-013 照样判不达成、交付照样判不通过。R2-F01 花整条收口建立的「有上界的短清单」批准机制，与 R2-F02 钉死的 M_min = 7 在同一份 spec 内互相注销，spec 未登记这一互斥（`:434` SC-001 只写了「两条必须合读」，说的是 SC-001 与 SC-013 的关系，不是 FR-060 与 SC-013 的关系）。

**问题二：同一个 M_min = 7 对另外 36 条核心集 FR 完全无约束。**

承 B-1 构造 P2 的分区核算，核心集 63 条中：

| 分区 | 条数 | 裁剪对 M 的影响 |
|---|---|---|
| 七个完整需求项覆盖 | **27** | 裁一条即 M ≤ 6 < M_min ⇒ 不达成（零余量） |
| 需求项 2 的核心侧（`FR-008` / `FR-009` / `FR-064`） | **3** | 该项已计「部分」不入 M ⇒ **无影响** |
| 无任何需求项归属（`FR-034~063` + `FR-065~067`） | **33** | **无影响** |

核对式：27 + 3 + 33 = **63 条**，单位：FR 条。**自由面 = 3 + 36 − 3 = 36 条，占核心集 36 ÷ 63 = 57.1%。**

也就是说 M_min = 7 这一个标量，在边界 A 的 63 条核心集上同时表现为**两个极端**：对 42.9% 的 FR 严到零余量（连一条都不能裁，使裁剪准入机制空转），对 57.1% 的 FR 松到完全不可见（含 `FR-052/053` 门不可绕过、`FR-059/060/061` 反稀释机制自身、`FR-042~045` 降级判定、`FR-054~058` 冲突收编、`FR-046~051` 回归护栏）。**一个定义在只覆盖半数 FR 的分区上的标量，无法表达对边界 A（分区单位是 FR 条）的一致下界**——这正是判据问的「M_min 是否与边界一致」，答案是否。

**问题三（判据特别点名的「需求项 2『部分』怎么计」）：口径本身自洽，但它是上界退化的直接成因，且 spec 未登记。**

`:468` SC-013 与 `:709` 对「部分」的处置逐字一致：「部分实现的第 2 项**不计入 M**（M 的口径是「被 Phase 认领且在 verify 中判为『已实现（附证据）』的需求项数」，部分实现不构成整项已实现）」。**该口径本身无歧义，且两处逐字相同**——这一点对得上。

问题在于它的推论没有被写出来：把需求项 2 从 M 的可能取值里剔除之后，`M ≤ 7` 成为恒等式，于是 `M_min = 7` 不再是「下界」而是「唯一合法取值」。`:468` 却仍把它表述为「**M_min = 7 排除的是「合规的零交付」与「大幅稀释」两种形态**」——按上表，它对 57.1% 的核心集 FR 连「大幅稀释」都排除不了（33 条全裁 ⇒ M 仍为 7），对另外 42.9% 则排除了包括「裁一条」在内的一切裁剪。**该条自登记的强度上限段落只写了「不构成对交付质量的任何声明」，没有登记这个分区不均匀性。**

另附一处已被 spec 自己登记、我复核属实的口径外溢（**不计新增**）：`:799` 登记 mode 分层矩阵第 2 行的字面区间 `FR-008~FR-013` 不含 `FR-064`，而 SC-013 已把 FR-064 归入需求项 2，裁定「两处口径以 SC-013 与本章节的『需求项级口径』为准」。本轮核算即按 SC-013 口径执行（故 FR-064 计入分区、不计入上表的 33 条无归属）；换按矩阵字面区间则无归属数为 34、占核心集 54.0%，两个口径下结论方向不变。
