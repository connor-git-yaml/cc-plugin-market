### 仍成立的攻击构造清单（3 条，按严重度排序）

**A-1（源自 R1-C03）· 承重锚失效 — 冻结哈希与被冻结物在同一写面内**
攻击构造：verify 子代理持有 `Bash`（spec `:223` 自述可 `sed -i` 改写 `plan.md` 覆盖矩阵），在同一次推理中一并 `sed -i` 改写 tasks 制品里的冻结哈希；哈希是**内容哈希、可重算**，spec 全文未把它锚到 git object、签名或只读介质，比对因此仍然一致，FR-005 的「不一致须附强制说明」不触发。
严重度最高的理由：这条锚是本卡三处结论的共同承重点——`:223` FR-016 称它为「verify 改不动的位置」并据此把独立性口径从「未取得」留出升级路径；`:207` FR-006 撤销「拒绝人工结论」后，改称真正锚住冲突的是「FR-005 的 `GATE_TASKS` 矩阵哈希冻结」；`:56` 验收场景同口径。锚若不成立，C07 与 C01 的「诚实降级」实为「降级到一个同样不成立的替代锚」。
建议收口方向：把冻结值锚到 verify 改不动的介质（如 `GATE_TASKS` 时点的 git commit 对象 / 由编排器而非 verify 持有的比对源），或明文把独立性登记为「未取得且本卡不取得」，不再由 FR-016 / FR-006 引用哈希冻结作为锚。

**A-2（源自 R1-C06）· spec 自认未修 — 一行死 import 洗白可达性报警**
攻击构造：为新增导出符号 X 加一行 `import { X } from './x.js'` 而永不调用，生产侧即出现 import 点。`:214` FR-010 虽已把判据改为「无生产侧**调用点**」，但 `:216` FR-012 明写「词法层无法可靠区分『引用了符号』与『调用了符号』……**一行死 import 仍可能洗白报警**」，处置只是把该能力边界写进检查项输出处。
性质：落到的是 R1-C06 处置的第二支（诚实登记），第一支（判据层收掉）未实现。诚实登记降低了 over-claim 风险，但攻击面原样存在，且这正是 US-2 唯一「机械判据」卖点所在的检查。
建议收口方向：把「调用点」判据下沉到最小可行的词法调用形态匹配（`X(`、`.X(`、`new X(` 等）并对其漏报面另行登记，或在 SC 面上明确该检查只承担 FR-011 的阴性对照职能，不承担阳性完备性。

**A-3（源自 R1-C05）· 候选池入池步无留痕，同人自证仍成立**
攻击构造：写 plan 的人同时是执行候选池扫描的人；`:212` FR-008 的逐条留痕义务只加在**池内**（「执行者须对池中每一条显式判定……无留痕的排除视为未处置」），**入池那一步不产生任何留痕义务**。因此把自己那段延期承诺在扫描时直接不列入候选池，产物上与「池中确实没有这条」完全同形——正是本卡 FR-062 要治的「没跑与跑了且干净同形」问题，却未平移到入池步。
性质：R1-C05 的两半只修了一半（值枚举 → 候选池已修；判据写作者与被约束者同一人未动）。spec `:36` 亦自认「入池触发面本身仍是措辞驱动的，形态覆盖率未测量」。
建议收口方向：把 FR-062 的留痕标准平移到候选池入池步——扫描命令原文 + 其原始输出 + 池内条数须一并写入产物，「候选池为空」这一结论同样须附产生它的命令与输出。
