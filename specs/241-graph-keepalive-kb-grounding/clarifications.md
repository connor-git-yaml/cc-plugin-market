## C-001 FR-008「同一 phase 内最多刷新一次」的执行机制与 phase 边界

- **位置**：FR-008（"调用方在同一 phase 内对同一 projectRoot 最多触发一次刷新"）+ FR-009（CLI 接受可选 `--phase`）+ EC-13（"本 feature 不引入跨进程锁"）
- **两种以上可能解读**：
  - **A（读磁盘审计日志判定）**：CLI 子命令是无状态进程；每次调用先读 `.specify/graph-consumption-audit.jsonl`，过滤出 `projectRoot` 相同且 `phase` 相同的历史行，若已存在 `refreshAttempted: true` 的行，本次即便 `refreshPolicy=allowed` 也视同已刷新过，直接按 FR-008 语义把 `refresh-then-consume` 分支的效果降级为不再 spawn（走 EC-07 同款"只刷一次"逻辑）。
  - **B（完全交给调用方外部状态）**：CLI 本身不做任何"是否已刷过"的判断，`refreshPolicy` 参数的取值本身就是调用方（goal_loop 迭代内存 / 散文层单次 phase 脚本变量）算好后传进来的，CLI 收到 `allowed` 就无条件尝试刷新，"最多一次"完全靠调用方自己在同一 phase 内只调用一次时传 `allowed`、之后都传 `declined`。
  - **C（不传 `--phase` 时无约束）**：若调用方省略 `--phase`，FR-008 的"同一 phase"分组失去锚点，退化为无限制（每次调用都可能刷新）。
- **推荐解读**：A + 对 C 的显式兜底——**CLI 侧读审计日志做判定（A），且省略 `--phase` 时用固定 sentinel（如空串 `""`）当作一个分组键**，而不是关闭约束。
  - 依据 1：FR-010 已经要求"每次决策必须追加一条审计记录"，且 Key Entities #3 明确审计记录含 `phase` 字段——这份 append-only 日志本就是唯一可查的跨调用状态源，不需要另建锁文件（EC-13 明确禁止引入锁，但"读已有 append-only 日志"不是锁，不违反该约束）。
  - 依据 2：D2 要求 goal_loop 与散文层调用**同一份判定**，若"最多一次"完全外置给调用方（解读 B），意味着两条消费路径（goal_loop 迭代循环 / implement-verify 单次脚本）必须各自正确实现"是否已刷过"的记账逻辑，等于把决策逻辑拆成两份、正是 D2 明令避免的"两套逻辑漂移"。
  - 依据 3：EC-07 的集成测试要求"在脏工作树上连续跑两次决策 CLI，断言第二次不再 spawn 构建"——这条验证本身就是两次**独立进程调用**，只有 CLI 内部读审计日志才能在两次独立进程间生效；若逻辑在调用方内存里，两次独立 `node ... cli.mjs` 调用之间不共享内存，测试会通不过。
- **若按另一种解读实现会怎样**：
  - 若按 B 实现，EC-07/SC-007 的集成测试（连续两次独立 CLI 调用）会在第二次仍然 spawn 构建，因为 CLI 本身对"是否已刷过"零判断——SC-007 断言必然失败，除非测试脚本自己维护了状态传给 CLI（但 spec 原文明确是"运行决策 CLI 两次"，暗示两次都是外部黑盒调用）。
  - 若不给 `--phase` 缺省定义（放任 C 的"无约束"），会出现 goal_loop 或散文层调用方偶然漏传 `--phase` 时刷新次数不受限，重新引入 EC-08 警告的"每次调用叠加一次超时预算"问题。

## C-002 FR-006「目标为 TypeScript/JavaScript 源」与 FR-002 `coverageScope` 判据是否同一份白名单

- **位置**：FR-006（"`directCallers = 0` 且目标为 TypeScript/JavaScript 源"）+ FR-002 维度 4（`coverageScope` 判据 = "目标文件扩展名是否在图 walker 白名单内"，指向 O-5 的 `.ts/.tsx/.js/.jsx`）
- **两种以上可能解读**：
  - **A（同一份白名单，判断即冗余）**：FR-006 只会在 FR-003 行 13（`freshness=fresh` 且 `coverageScope=in-graph-scope`）触发，而进入这一行本身就已经保证目标扩展名在 `.ts/.tsx/.js/.jsx` 白名单内。因此 FR-006 的"目标为 TS/JS 源"条件对能走到这一行的输入永远为真，实现时**不需要再写第二套扩展名判断**，只需检查 `directCallers === 0` 即可触发 caveat。
  - **B（另立一套更窄的判断，比如只认 `.ts/.js` 不认 `.tsx/.jsx`）**：把"TypeScript/JavaScript 源"读成比 walker 白名单更窄的子集，需要新写一个独立的扩展名判断函数。
- **推荐解读**：A。
  - 依据：O-3 复核结论明确指出"调用抽取器不下钻实参箭头函数体"这一漏边形态发生在 `.ts` 文件（`kb-search.ts`），而 FR-006 caveat 的措辞红线目的（D7）就是要覆盖"图是新的、目标在图覆盖范围内，但仍可能因抽取器已知缺陷而漏边"这一态——它的适用范围天然就是"能进图的文件"，与 `coverageScope=in-graph-scope` 是同一集合。若另立一套更窄白名单，会产生两份可能漂移的扩展名判断（正是 D2 明确要避免的模式）。
- **若按另一种解读实现会怎样**：按 B 实现，会多出一个从未被 FR/EC/SC 提及、也无测试覆盖的第二白名单，未来 O-5 相关白名单调整时容易漏改其中一处，产生行为不一致但无测试能抓到的隐蔽 bug。

## C-003 FR-015 / D5「跨 ≥ k 个不同查询」中 `distinctQueries` 的判定键

- **位置**：D5（"某个归一化查询词只有跨 ≥ k 个不同查询出现过才允许进入 backlog"）+ FR-015（"仅输出满足跨 ≥ 2 个不同查询出现"）+ Key Entities #6（`occurrences` 与 `distinctQueries` 是两个不同字段）+ SC-011（"3 条同词记录来自 2 个不同查询"）
- **两种以上可能解读**：由于 FR-012/FR-013 明确规定**原始查询原文不落盘**（每条 no-hit 记录只存 `redactedQuery` 脱敏后的串，无 query-id / session-id 字段），"不同查询"在聚合阶段只能从 JSONL 记录本身的字段推导，存在两读：
  - **A（`distinctQueries` = 该词命中的 JSONL 行数，`occurrences` = 该词在这些行的原始查询串中出现的 token 次数，可能 > 行数）**：若同一次查询的原文本身包含该敏感词形态两次（例如一句话里出现两个邮箱都被替换成同一个 `<EMAIL>` 占位符），一行内 `redactedQuery` 可能重复出现该 token；`occurrences` 计的是 token 出现总数，`distinctQueries` 计的是产生这些 token 的**记录行数**（每行 = 一次查询调用 = 一次事件）。
  - **B（`distinctQueries` 与 `occurrences` 是同一个数，字段拆分只是冗余）**：既然每条 JSONL 记录本身就是"一次查询"的事件记录，"出现次数"与"跨多少次查询出现"理应永远相等，两个字段只是同义重复。
- **推荐解读**：A。
  - 依据 1：Key Entities #6 把 `occurrences` 与 `distinctQueries` 列为两个独立字段，若二者恒等（解读 B），FR-015 没有理由要求实现分别输出——字段设计本身暗示了它们可能不同，只有解读 A 能让两个字段在语义上分道扬镳。
  - 依据 2：SC-011 明确写"3 条同词记录（来自 2 个不同查询）"——若按 B（记录=查询一一对应），3 条记录只能来自 3 个不同查询，不可能是 2 个；这句验收描述本身只有在"记录数可以多于查询数"（即单条记录内该词可重复出现，或存在其它使记录数与查询数不一致的机制）的前提下才成立，直接印证了 A。
  - 依据 3：D5 的隐私目的是"防止一次性泄露的敏感串被当作缺口信号"，按记录行数（等价于事件次数）计 `distinctQueries` 与这一目的完全吻合——每行本就是一次独立的查询事件，用行数作为"跨多少次查询"的计数键，语义最直接、无需引入 spec 未定义的 session/query-id 概念。
  - **实现建议**：`occurrences` = 该归一化词在所有匹配行的 `redactedQuery` 中出现的 token 总次数（同一行内重复计数）；`distinctQueries` = 包含该词（至少一次）的 JSONL 行数（同一行不重复计数）。
- **若按另一种解读实现会怎样**：若按 B 实现（两字段恒等），SC-011 给定的 fixture（"3 条同词记录来自 2 个不同查询"）会导致实现者无法理解如何构造该 fixture、或干脆把 `distinctQueries` 硬编码等于 `occurrences`，使 k-匿名阈值的判定退化为纯粹的"出现次数 ≥ 2"，弱化了 D5 意图区分"同一查询内重复 vs 跨多次查询重复"的隐私粒度。

## C-004 FR-009 `--phase` 参数缺省时的默认分组键

- **位置**：FR-009（"接受 projectRoot 与可选的 `--phase`"）+ Key Entities #3（审计记录含 `phase` 字段，未说明可否为空）
- **两种以上可能解读**：
  - **A（缺省时用固定 sentinel 值，如空串 `""` 或 `"unspecified"`，纳入 C-001 的分组判定）**：省略 `--phase` 不等于放弃 FR-008 约束，只是把所有未指明 phase 的调用聚成同一组，"同一 projectRoot + phase=unspecified"内仍然最多刷新一次。
  - **B（缺省即豁免 FR-008 约束，每次调用各自独立判定）**：`--phase` 未传时，FR-008 的"同一 phase 内最多一次"逻辑不生效，退回"是否允许刷新"完全由 `refreshPolicy` 单独决定。
- **推荐解读**：A，理由已在 C-001 依据 3 中给出（EC-08 明确警告"避免每次调用叠加一次超时预算"，该风险与是否传了 `--phase` 无关，不应因为省略一个可选参数就重新暴露）。
- **若按另一种解读实现会怎样**：省略 `--phase`（这很可能是散文层单次脚本调用的默认用法，因为它没有 goal_loop 那样天然的"轮次"概念）会导致 FR-008 约束事实上只在 goal_loop 路径生效、在散文层路径形同虚设，产生两条消费路径行为不一致的隐蔽差异。
