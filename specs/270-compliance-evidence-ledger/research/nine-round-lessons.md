`specs/216-*/spec.md:149-152` 的 GATE_DESIGN Q3 明确列出选项 (b)「**维护独立证据账本绕开主 transcript 依赖**」，并**否决**，理由三条：

> ⚠️ 注意措辞差异：F216 写的是"独立证据账本"，**不是** "hook 侧实时账本"；且**未找到**任何文档明确否决过"hook 侧实时账本"这一具体形态。不得把 F216 的否决**过度**解读为对本方案的否决，也不得**假装它不存在**。

## 2. 🔴 第二重要：PostToolUse hook 曾**静默失效多年无人发现**（F245）

`specs/245-*/fix-report.md:5,23`：`post-tool-use-format.sh` 因同一 payload 取值缺陷，**自 F084 起从未生效**，且**零测试覆盖**，直到 F245 才被发现修复。

> **对 F270 的直接要求（新增设计约束 L-1）**：账本采集器**必须有活性自检**。
> 否则失效模式是**最坏的一种**：采集器静默不写 → 账本恒空 → 判定器按「账本缺席」回退 → 门禁静默退回改动前强度 → **没有任何人会发现**。这与 F245 的历史完全同型，且因为账本是本需求的地基，后果更严重。
> 自检的形态留 plan，但 spec 必须把「采集器活性可被观测」列为功能需求，而不是运维建议。

## 4. 跨轮根因模式中，**直接命中账本设计**的三条

- **M4 · 存在性判据冒充关联性/归属判据**
  实例：F225 写指示符跨段互相背书；F257 把 `usable()`（制品**存在性**）当作**会话归属**判据（`257/fix-report.md:22-23`：「short-name 跨编号、跨会话、跨人都可能重复，**不蕴含归属**」）。
  → **对账本**：账本条目"存在"≠"属于本轮/本次 fix"。归属必须由**独立字段**承担（`prompt_id` 分组、锚点之后的序位），且该归属判据要单独论证，不能靠"在账本里"顺带成立。

- **M5 · 载体/通道复用而不重做安全论证**
  实例：F257 缺陷 2 —— fail-**open** 方向的 `inFlightDeferCount` 被挂进为 fail-**closed** 设计的 `blockCount` 状态载体，「同一存储、同一回落语义、**相反的失效方向**——载体的安全论证没有随字段语义一起重新做」（`257/fix-report.md:37`）。
  → **对账本**：账本是**新载体**。凡复用既有状态文件、既有诊断码、既有闸门载体承载账本语义的地方，**必须重做失效方向论证**。必答②裁决表里每一条「改造」都是这个风险点。

- **M6 · 只验判定器自己的测试，发现不了判据与真实语义不一致**
  实例：F231 第 9/10 轮**三次绿色测试掩盖漏洞**——正向断言把错误语义编码进回归集，448/448、926/926 全绿反而把误放行固化。原文：「**全绿在这里是反指标**」（`231/fix-report.md:169,186,222`）。F257：「形式证明与实证互相背书出了一个假结论」（`:263`）。
  → **对账本**：这正是必答④要求**真实会话录制语料**的根本理由。合成 fixture 由我们按自己的理解构造，**天然只能验证"实现符合我们的理解"，验证不了"我们的理解符合 harness 真实行为"**。

## 5. fail-open / fail-closed 的既有原则（**不得回退**，按时间顺序）

1. **F208 起点**：整体 fail-open 是**产品约束**——「宁可漏拦一次，不可全局误伤或阻塞全部会话」（`208/spec.md:165`），必须落 degraded 诊断。「**Stop hook 不可 brick 会话**」（`216/spec.md:149`）。
2. **F224 FR-004a**：**fail-open 必须按维度收窄，不得整体短路**（`224/spec.md:108`）。F228 复述为通用教训：「整体放行 = 送出一条可主动触发的绕过」（`228/fix-report.md:115`）。
3. **F230**：**降级下界必须被合规合同蕴含**——凡 `judgeCompliance` 可能判合规的构成，降级都必须放行，否则出现状态依赖不一致（`230/fix-report.md:118`）。
4. **F231**：**可用性即安全属性**——判定器跑在同步 Stop hook，挂死 → 门禁不可用 → 可能异常 fail-open。任何新判据必须给出**最坏复杂度证明与性能回归锚点**，不能只证"判得对"（`231/fix-report.md:223`）。
   → **对账本**：读取账本是新增 I/O，**必须**给出账本体积上界与最坏读取耗时锚点。账本无限增长 = 把 Stop hook 拖慢 = 新的可用性风险。
5. **F256**：**持久化失败即不推迟**（维持不了计数就没有上界，fail-closed）；「顺序约束：**先有界化，再考虑放宽**」（`256/fix-report.md:214,238`）。
6. **F257**：**方向不对称是刻意的**——见证窗口用**最晚**锚点、闸门三用**最早**展开，「两侧各自 fail-closed，不是需要对齐的疏漏」（`257/fix-report.md:304`）。
7. **有界化 ≠ 消除**（明确写下）：删状态文件绕过闸门二**仍然有效**，只是从"永久免于裁决"降级为"约 140 轮内免于裁决"（`256/fix-report.md:229-230`）；闸门三的 420 上界「字面有界成立，但实际约束力接近于无」（`257/fix-report.md:181`）。
   → **对账本**：必答②废除闸门二时，不能把"有了权威字段"当成"上界不需要了"。上界的作用是**兜住探测本身失效**的情形。

## 7. 主线程判断：本需求相对九轮史的**结构性差异**

九轮全部是**在同一证据源（transcript 文本）上改判据形态**，故 M1（形态可等价变换）反复复现。
F270 换的是**证据源本身**，且新证据源具有九轮判据都不具备的两个性质：

1. **由 harness 进程写入**，不经被判方生成域（对比已证伪路线 #21：transcript 文本全在被判方自由生成域内）；
2. **`background_tasks` 等字段被判方无法回退**（对比已证伪路线 #22：任何以被判方可控行号为基准的量都可被回退）。

**但这不构成"这次一定对"的理由**——诚实结论是：
- 账本文件**事后可被改写**（必答①已登记为残余风险），故它的下界只比 transcript **稍高**，不是质变；
- 真正的质变只发生在 `background_tasks` / `stop_hook_active` 这类**被判方完全不可写**的 harness 字段上。
→ **推论**：凡能用 harness 字段直接判定的，优先用 harness 字段；账本承担 harness 字段覆盖不到的那部分（工具调用序列），并诚实接受其"只防疏忽"的下界。这与必答①的结论一致，此处从九轮史给出**独立的第二条论证路径**。
